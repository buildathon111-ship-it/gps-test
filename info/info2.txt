PROJECT: AGRIVISION — Automatic Agricultural Field Boundary Mapping & Digital Twin Calibration

GOAL
Build a standalone, browser-based prototype for AGRIVISION that can take GPS coordinates collected while an agricultural rover travels around the boundary of a farm, clean and process the GPS data, reconstruct the field boundary, calculate the covered area, and display a clean digital representation of the agricultural land.

This is the second major software module of AGRIVISION.

The real GPS module is NOT available yet, so the system must initially work with simulated GPS data. The architecture must later allow the simulated GPS source to be replaced by the real ESP32 + GPS telemetry without changing the processing pipeline.

==================================================
CORE CONCEPT
==================================================

AGRIVISION should support an initial "FIELD CALIBRATION / MAPPING RUN".

The farmer places the rover at the desired home/base position.

The rover then travels around the boundary of the agricultural field.

During this run, GPS coordinates are continuously collected:

Latitude
Longitude
Timestamp
GPS accuracy if available

Example:

P1 → P2 → P3 → P4 → P5 → P1

The software must convert this raw GPS trajectory into a clean field boundary polygon.

Pipeline:

      ↓

      ↓

      ↓

      ↓

      ↓

      ↓
Digital Twin / Field Map

==================================================
IMPORTANT GPS REALITY
==================================================

Do NOT assume GPS coordinates are perfectly accurate.

Consumer GPS can contain noise, sudden jumps and inaccurate points.

The system must therefore be designed to handle:

- noisy coordinates
- duplicate coordinates
- sudden unrealistic jumps
- very small movements
- GPS accuracy changes
- temporary GPS glitches
- missing coordinates
- irregular sampling intervals

Do NOT simply connect every raw GPS point and call that the field boundary.

The resulting boundary should be visually clean and stable.

==================================================
GPS DATA VALIDATION
==================================================

Implement validation before using a point.

Reject points when:

- latitude is invalid
- longitude is invalid
- coordinates are missing
- coordinates are outside valid geographic ranges
- timestamp is invalid when required
- movement between points is physically implausible

Do NOT silently discard data.

Keep useful processing statistics such as:

Raw points: 500
Valid points: 481
Rejected points: 19
Filtered points: 463

==================================================
OUTLIER / JUMP DETECTION
==================================================

Detect unrealistic GPS jumps.

Example:

Point A
↓
Point B
↓
Point C

If B suddenly appears hundreds of metres away from A and C while the rover is supposed to be moving slowly, treat it as a potential GPS outlier.

Use configurable thresholds.

Make these thresholds clearly defined in the code so they can later be tuned using real NEO-6M data.

Do not assume one perfect threshold will work for every deployment.

==================================================
POINT SIMPLIFICATION
==================================================

After filtering and smoothing, reduce unnecessary points while preserving the shape of the field.

The final polygon should not contain thousands of unnecessary points if a smaller number can represent the same boundary accurately.

Keep:

Raw GPS points

separate from:

Processed boundary points.

==================================================
BOUNDARY RECONSTRUCTION
==================================================

Generate a clean closed polygon from the processed rover trajectory.

The final polygon should:

- follow the rover's actual surveyed path
- be closed
- avoid obvious self-intersections where possible
- remove unnecessary noise
- represent the field boundary cleanly

Do NOT simply calculate a convex hull unless clearly appropriate.

An agricultural field can be concave or irregular.

Preserve meaningful field shape.
